# 未来分步开发计划

本文件说明为了实现整体构架，未来的分步开发计划应该怎么设计。

## 总体开发原则

1. **先骨架，后肌肉**：先完善治理层（三省），再丰富业务层（六部）
2. **先闭环，后优化**：先实现完整工作流闭环，再优化各个环节
3. **先配置，后代码**：优先通过配置/文档与少量注册类代码实现；真正的新能力再进入代码开发
4. **先验证，后推广**：每阶段完成后充分验证，再进入下一阶段

## 阶段划分

### Phase 0：准备阶段（已完成）
- [x] 完成整体设计文档
- [x] 调整纲领性规则文件
- [x] 制定计划文件

### Phase 1：最小可运行版本（MVP）
**目标**：实现"分拣—规划—审议—派发—执行—回奏—朝会—监察"的闭环

**时间预估**：1-2 周

**主要任务**：
1. 更新所有现有 Agent 的 SOUL.md 为投资版职责
2. 新增御史台 Agent（SOUL.md + 配置）
3. 修改 dashboard/server.py 的 `_AGENT_DEPTS`（少量注册类代码修改）
4. 补充 `_ORG_AGENT_MAP` 的早朝官和御史台映射（少量注册类代码修改）
5. 验证标准即时任务链可以正常运行
6. 验证门下省封驳功能
7. 验证任务可以正常流转到完成状态

**验收标准**：详见 [plans/02_minimum_viable_product.md](02_minimum_viable_product.md)

### Phase 2：专项机构扩展
**目标**：增加皇城司和发改委，实现资讯中台和长期逻辑跟踪

**时间预估**：2-3 周

**主要任务**：
1. 新增皇城司 Agent（SOUL.md + 配置）
   - 资讯总管
   - 议题整理官
2. 新增发改委 Agent（SOUL.md + 配置）
   - 长期逻辑官
   - 行业景气官
3. 修改 dashboard/server.py 的 _AGENT_DEPTS，增加皇城司和发改委
4. 补充 _ORG_AGENT_MAP 的皇城司和发改委映射
5. 实现《议题卡》模板
6. 实现国策议题链（延迟汇报）工作流
7. 实现《行业逻辑榜单》输出
8. 验证国策议题可以正常入池、跟踪、汇报

**备注**：国策库、议题卡、行业逻辑榜单可以在更早阶段先准备字段定义或模板，但真正的“入池—跟踪—定时汇报”功能，以本阶段实现为准。

**验收标准**：
- [ ] 皇城司可以整理用户想法为《议题卡》
- [ ] 国策议题可以进入国策库
- [ ] 发改委可以输出《行业逻辑榜单》
- [ ] 国策议题可以在指定时间汇报

### Phase 3：模板与流程深化
**目标**：完善所有输出模板，深化盘前/盘中/盘后流程

**时间预估**：2-3 周

**主要任务**：
1. 创建所有模板文件（详见 [plans/01_config_only_modifications.md](01_config_only_modifications.md)）
2. 完善盘前流程：
   - 盘前简报生成
   - 每日重点清单（不超过 3 个）
   - 个性化行为提醒
3. 完善盘中流程：
   - 计划内机会监控
   - 触发条件提醒
   - 替代成本审核流程
   - 冷静期流程
4. 完善盘后流程：
   - 执行结果收集
   - 执行偏差记录
   - 问责复盘单生成
5. 完善周度流程：
   - 周度大朝会
   - 成长报告输出
   - 遗弃机会检查

**验收标准**：
- [ ] 所有模板文件已创建
- [ ] 盘前流程可以自动生成盘前简报
- [ ] 盘中流程可以监控触发条件
- [ ] 盘后流程可以生成问责复盘单
- [ ] 周度流程可以输出成长报告

### Phase 4：定时任务与配额治理
**目标**：实现定时任务链和配额治理功能

**时间预估**：2-3 周

**前置说明**：
- `data/scheduled_tasks.json`、`data/quota_config.json` 等文件可以在更早阶段先定义 schema。
- 但“文件已存在”不等于“功能已实现”。真正的 Cron 调度、配额查询、节流逻辑、差异对比，应以本阶段落地为准。

**主要任务**：
1. 实现定时任务表配置（`data/scheduled_tasks.json`）
2. 实现 Cron 调度触发
3. 实现配额配置（`data/quota_config.json`）
4. 实现礼部配额官的节流建议功能
5. 实现定时报告后的差异对比
6. 修改或新增相关 API 端点（如需）
7. 可能需要新增前端组件（如需）

**验收标准**：
- [ ] 定时任务可以按 Cron 触发
- [ ] 配额紧张时可以提出节流建议
- [ ] 定时报告后可以输出差异对比摘要
- [ ] 关键报告优先级高于一般讨论任务

### Phase 5：功能完善与优化
**目标**：完善剩余功能，优化用户体验

**时间预估**：3-4 周

**主要任务**：
1. 实现吏部行为画像的持续更新
2. 实现刑部越权稽核的自动化
3. 实现御史台成长监察的周度报告
4. 实现工部技术统计和回测功能
5. 优化任务流转的用户体验
6. 优化看板的显示和交互
7. 增加更多的验证和测试用例

**验收标准**：
- [ ] 吏部可以持续更新用户行为画像
- [ ] 刑部可以自动稽核越权行为
- [ ] 御史台可以输出周度成长报告
- [ ] 工部可以进行技术统计和回测
- [ ] 用户体验得到明显改善
- [ ] 测试覆盖率达到预期目标

### Phase 6：生态与扩展
**目标**：构建生态系统，支持更多扩展功能

**时间预估**：4-6 周

**主要任务**：
1. 实现更多的 Skills（技能）
2. 支持更多的数据源接入
3. 实现与外部系统的集成（如券商 API、数据源等）
4. 编写更多的使用文档和教程
5. 建立社区和贡献者指南
6. 考虑移动端适配或 PWA

**验收标准**：
- [ ] 有足够丰富的 Skills 库
- [ ] 支持多种数据源接入
- [ ] 有完整的文档和教程
- [ ] 有活跃的社区贡献

## 风险与应对

| 风险 | 影响 | 概率 | 应对措施 |
|-----|------|------|---------|
| Agent 职责边界不清晰 | 高 | 中 | 在 SOUL.md 中明确定义禁止事项，建立越权稽核机制 |
| 状态机流转复杂 | 中 | 低 | 保持现有状态机不变，通过配置实现新功能 |
| 前端修改工作量大 | 中 | 中 | 优先通过配置实现，必要时才修改前端 |
| 测试覆盖不足 | 高 | 中 | 每阶段完成后进行充分测试，建立自动化测试 |
| Token 消耗过高 | 中 | 高 | 优化提示词，合理设置配额，实现节流功能 |

| Phase 3 | 1-2 人 | 2-3 周 | Phase 2 完成 |
| Phase 4 | 2 人 | 2-3 周 | Phase 3 完成 |

| Phase 6 | 2-3 人 | 4-6 周 | Phase 5 完成 |

## 总结

按照这个分步开发计划，我们可以：

1. **快速交付价值**：Phase 1 就可以交付一个可用的 MVP
2. **降低风险**：每个阶段都有明确的验收标准，可以及时发现问题
3. **灵活调整**：可以根据实际情况调整各阶段的优先级和时间
4. **持续改进**：每个阶段都在前一阶段的基础上进行，不断完善

预计整体完成时间：**3-4 个月**（从 Phase 1 开始计算）
